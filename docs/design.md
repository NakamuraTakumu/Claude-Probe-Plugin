# probe の設計

この文書は、probe を保守する人に向けて実装を説明する。使い方は [README](../README.md) を見る。

probe は、読み取り専用の調べものツール `probe` を、セッション内の標準サブエージェント（haiku）で動かす。外部の CLI も `claude -p` も使わない。

プラグイン名は `probe`。`claude-` で始まる名前は予約済みで `claude plugin validate` が拒否するため、`claude-probe` にはできない。ツールは `mcp__probe__probe`、エージェントの種類は `probe:probe`。

## 何をするか

- ツール `probe`：`questions`（文字列の配列、1件以上）、`cwd`（省略可）、`max_chars`（省略可、整数 500〜8000、既定 2000。1件ごとの結果の字数の上限で、すべての questions に効く）。各問いを隠しエージェント `probe:probe` として起動し（同時に最大16件。セッションの上限 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` に当たって断られた問いは、動いている子が終わるのを待って起動し直す。この呼び出しの子が1つも動いていないまま問いの時間（15 分）が過ぎたら、その問いは `ERROR: 開始できなかった`）、1件のときは答えの本文だけを、2件以上のときは `〔問い 1〕`、`〔問い 2〕` … の見出しで並べた1つの文字列で返す。一部が失敗したらその欄（1件のときは本文）に `ERROR: ...` を書く。全部失敗したら deny。フック自体が失敗したとき（例外、フックの持ち時間の超過）は、その種類と理由を書いた deny を返す（例：「probe の実行に失敗した（フックの持ち時間を超えた）。」）。問いごとに15分でタイムアウトし、`TaskStop` で止める。
- 親のモデルに見せる文面：親から見て委任先ではなく Bash のような道具に見えるよう、説明文にはツールの性質（何をするか、何に向くか、何を返すか）だけを書き、引数の使い方は引数の説明に、使う人の方針は usage.md に置く。説明文と引数の説明、子への指示（`probe:probe` の指示、各問いの末尾の字数の上限、差し戻しの依頼）には「サブエージェント」「エージェント」「タスク」を使わない（テストで確かめる）。この README のように実装を説明する文書は対象外。
  - 説明文：`読み取り専用のシェルで調べて、結論か関係する原文の引用だけを返す。ファイルの検索、コマンドやテストの実行、Web 検索ができ、条件を明示すれば分岐を含む手順も任せられる。向くのは、どこにあるか分からないものを広く探すとき、多くのファイルにまたがるとき、長い出力（ログ、コマンドの出力）から要点だけ欲しいとき、Web で調べるとき。判断は、基準を問いに書けるなら任せられる。会話全体の文脈や好みに依る判断は任せず、材料集めに使う。答えの事実はそのまま使ってよい。確かめていない推測には「推測」と書かれ、見つからなかったときは探した範囲が書かれる。〔〕 は probe が付ける印。`
  - `questions`：`知りたいこと。1件に1つの仕事と、返してほしい形（ファイル:行と引用、件数、出典の URL など）を書く。長くなりそうな一覧は「件数と先頭 N 件」のように頼む。複数書くと並列に処理され、結果はまとめて返る（最大16件同時。同じディレクトリでビルドする問いは並べない）。`
  - `cwd`：`実行ディレクトリ。省略すると現在の作業ディレクトリ。`
  - `max_chars`：`1件ごとの結果の字数の上限（500〜8000、省略すると 2000）。引用や一覧が多いときは上げる。超えると書き直させ、それでも超えれば切り詰める。`
  - `context`：`false なら依頼主の会話を渡さず、問いだけを渡す（省略すると true）。渡すのは直近の数往復の本文だけで、ツールの結果は渡らないので、前の結果で分かったパスや名前は問いに書く。問いだけで足りるなら false にする（会話に引きずられず、安い）。`
  - `effort`：`調べる側の考える深さ（省略すると low）。手順の多い調べものや、難しい判断には medium 以上。`
- 結果の長さ：各問いの末尾に「（結果の上限: N 字）」を足して起動する（`probe:probe` の指示には「結論を先に。既定では 2000 字以内。依頼に長さや形の指定があればそれに従う。経過・コマンド・注意書きは頼まれない限り書かない」とある）。答えが N 字を超えたら、切り詰める前に、同じエージェントに `$.session.send({ to: { agentId }, text })` で「結果が N 字で、上限 M 字を超えた。結論を先に、M 字以内に書き直して。必要な情報だけ残す。」と頼む（終わったエージェントは会話の続きから再開される）。新しい答えはまた `turn.complete` で受け取る。差し戻しは1つの答えにつき最大2回。それでも超えたら先頭 N 字に切り詰めて `〔切り詰め：元は X 字〕` を付ける。送れなかった、書き直しがエラー・空・中断だった、書き直し中にタイムアウトしたときは、直前の答えを同じように切り詰める。15 分のタイムアウトは起動から数え、差し戻しの時間も含む。差し戻しの回数は結果に書かない。
  - 終わったエージェントを再開するとき、エンジンはそのエージェントの型が `agent.offer` で提供されているかを確かめる（提供されていないと「Agent type 'probe:probe' is not offered in this session.」で SendMessage が失敗する）。`probe:probe` は親のモデルから隠しているので、差し戻しを送っている間（送る前から、書き直しが終わるまで）だけ `agent.offer` を true にする。親のターンはその間ツール呼び出しの中にいるので、型が親のモデルに見えることはない。
  - 差し戻しを頼めなかった（送れない、書き直しがエラー・空・中断、3 分たっても終わらない）ときも、直前の答えを切り詰める。probe は自分ではモデルを呼ばない。答えを書くのは、ツールの出力を見た子だけにする（会話を持たない別の呼び出しに縮めさせると、引用や「推測」の印を書き換えるおそれがあり、差し戻す相手もいない）。
- 使い分けのルール：使う人の方針（品質や速度より quota を優先する、など）を書いた `usage.md` を、`prompt.attachment`（type `model`）で、エンジンの model 添付（「You are powered by the model named …」で始まる、モデル名を伝えるメッセージ）の後ろに足す。この添付は main の会話にも、Agent ツールで起動したサブエージェント（Explore、general-purpose など）にも入るので、どこでも同じ文が同じ場所に入る。probe の子には足さない（probe を呼べないので要らない）。添付には `agentId` が付くので、`$.agent.list()` の種類か起動したプラグインで子を見分ける（子の最初のリクエストの時点で一覧に載っていることを 2.1.319 で確かめた）。
  - 添付への答えはプロセスの中で使い回され、`$.ui.invalidate("prompt.attachment")`、圧縮、新しいプロセスでの再開のときに聞き直される（2.1.319 で、記録に残る送ったリクエストの写しで確かめた）。そのため、動いているセッションにも、変えた usage.md やモードが次のリクエストから届く。文面が変わらなければ送る中身も変わらないので、聞き直してもプロンプトのキャッシュは外れない。usage.md はセッションごとに1回だけ読み、`/probe-mode` で読み直す。core がこの添付を出さないとき、読めない・空のときは何も足さない。プラグインを外せばルールも消える。
  - 0.4.0 までは、システムプロンプトの節 `env_info_model` に `prompt.section` で足していた。しかしこの節が作られるのは、新しい model 添付を作るとき（セッションの最初と、モデルが変わったとき）だけで、その文面は添付の行に保存され、圧縮の後も再開の後もそのまま付け直される。そのため、`/probe-mode` や `/reload-plugins` を打っても、動いているセッションには届かなかった（2026-11-09 に記録で確かめた）。保存された文面に残るそのルールは、見出し「# probe の使い分け」から後ろを除いてから、今のルールを足す。
- モード：`/probe-mode save|handy` で、usage.md のどの行を入れるかを切り替える。今の usage.md では、見出しのほかは save の行と handy の行に分かれている。handy で入るのは「自分で正確に読む必要があるものは自分で読む」の1行だけである。説明文には両方のモードで成り立つことだけを書き、片方のモードでしか成り立たないことは usage.md のそのモードの行に書く（そうすれば、一方が他方を打ち消す文が要らない）。`<!-- save -->` か `<!-- handy -->` の行から `<!-- all -->` の行までは、そのモードのときだけ入り、ほかの行は両方に入る。モードは `$.store` に残り、後のセッションもそのモードで始まる。既定は handy である。save は「品質や速度より quota を優先する」「ほかの指示より probe を優先する」という方針を親に届けるので、使う人が `/probe-mode save` で選ぶ。切り替えたセッションでは次のリクエストから model 添付の文面が変わる（会話の先頭近くが変わるので、プロンプトのキャッシュが1回外れる）。`/probe-mode` は引数なしでも usage.md を読み直すので、編集した usage.md を起動し直さずに効かせられる。
- 呼び出しごとの指定：`context: false` なら質問だけを渡し（「## 背景」を付けない）、その呼び出しの子は context ツールを断られる。`effort: "low" | "medium" | "high" | "xhigh" | "max"` は、その呼び出しの子のモデルリクエストごとに `turn.step` で付ける（`$.agent.spawn` は effort を取らないため）。省略すると AGENT_SPEC の low。
- 背景：probe が呼ばれるたびに、呼んだ会話（メイン、または呼んだ別のループ）から直近のユーザー発言 3 件とその間・その後の assistant の本文を取り出し（`context` と同じく本文だけ。道具の出力と `<system-reminder>` は除く。合計 1500 字まで、超えたら古い方から削る）、各問いの前に「## 背景（依頼主との直近の会話）」として付け、問い本体は「## 質問」の下に置く。会話は 1 回の呼び出しにつき 1 回だけ読む。読めない、本文がないときは背景なしで続ける。子への指示は「背景は参考。足りないときだけ context ツールで読む」。
- 依頼主の会話を読むツール `context`（`mcp__probe__context`）：probe の中だけで使う。入力は `grep`（本文に含まれる文字列か正規表現、大文字小文字は区別しない）、`last`（最新から N 件、既定 5、上限 50。grep で絞ったあとに数える）、`max_chars`（返す字数、既定 3000、200〜8000）で、どれも省略できる。probe を呼んだ会話（メインの会話、または probe を呼んだ別のループ）の user と assistant の本文だけを古い順に `### user` / `### assistant` の見出しつきで返し、道具の出力と `<system-reminder>` は除く。上限を超えたら新しい方を残して古い発言を省き（印を付ける）、1 件だけで超えるときはその発言の末尾を残す。呼び出しを許すのは probe の子だけ（起動した probe 呼び出しの依頼主を覚えている）。それ以外、親のモデルからの呼び出しも拒否する。型定義にツールを隠す手段（`tool.offer` に当たるもの）はないので、親からは完全には隠せない。代わりに `isDeferred: true` で ToolSearch の裏に置き（親の prompt にスキーマが載らない）、説明文を「probe の内側専用」にしてある。probe の子の道具には ToolSearch がないので、`tools` に名前を入れたこのツールはそのまま見える（本体のコードを読んだ限りの推測で、実機では未確認）。子への指示には「背景が分からないときだけ読む」と書いてある。ファイルへの書き出しはしない。
- エージェント `probe:probe`：haiku、道具は Bash・Read・Grep・Glob・WebSearch・WebFetch、effort は low、CLAUDE.md は読まない。`agent.offer` で親のモデルからは見えない。
- 読み取り専用（`PROBE_SANDBOX=off` のときを除く。下の節を見る）：probe のサブエージェントの Bash は、次のサンドボックスのうち、この環境で動く最初のもので包んで実行する（どれが動くかは probe の呼び出しごとに、その子の最初の Bash で1回確かめる。前の呼び出しで確かめた結果は使わない）。どれもファイルシステムを読み取り専用にし、ネットワークを切る。一時ファイル（`mktemp`）はそのコマンドの間だけ置ける。Web を調べるのは WebSearch・WebFetch で、これは Bash ではないので auto mode の判定を受けて使える。
  - bwrap（Linux）：`bwrap --ro-bind / / --dev /dev --proc /proc --setenv TMPDIR /dev/shm --unshare-net --die-with-parent -- bash -c '...'`。/tmp も含めて全体を読み取り専用にする。書けるのは bwrap がそのコマンド用に作る /dev の中だけで、`TMPDIR` をその /dev/shm に向ける。コマンドが終わると消え、ホストには何も残らない。
  - sandbox-exec（macOS）：コマンドごとに `mktemp -d` で作ったディレクトリ（`TMPDIR`。/tmp ではなく macOS のユーザーごとの一時ディレクトリの下）と /dev/null・端末だけに書ける Seatbelt のプロファイルで `bash -c '...'` を包み、終わったらそのディレクトリを消す。この環境では試せていない。
  - srt（Windows。先に `claude sandbox install` を済ませ、`srt` を PATH に置く）：`srt -c '...'`。書き込みと、Bash からのネットワークを止める（srt の設定には「どこでも許す」がない。WebSearch・WebFetch は Bash ではないので使える）。この環境では試せていない。
  - どれも動かないとき：包まずに渡し、`tool.check` で、Bash 自身が読み取り専用と判定したコマンド（`ls`、`cat`、`grep`、読むだけの `git` など）だけを通す。テストやビルド、python などは断られる。
  - Edit・Write・NotebookEdit は拒否する。`run_in_background` の Bash も拒否する。関所のフックが例外を出したときは、probe（または分類できない）サブエージェントの呼び出しを拒否側に倒す。
- 二重配送の抑制：`$.agent.spawn` のサブエージェントはバックグラウンドで動き、終わると自分の答えを SubagentHandback ツールで親に返す。これは `session.send` を通らず、親のキューに peer のメッセージとして直接入るので、そのままだとツールの結果と答えが二重になる。親のターンが走っている間は、その配送が `queued_command` という添付（「Another Claude session sent a message while you were working」の system-reminder。中身は `<agent-message from="agentId">` と `[Subagent hand-back] …`）になる。止まっているときはキューから取り出されて `prompt.submit` を通る（`<cross-session-message from="…">`）。そこで送り主が probe のサブエージェントの hand-back だけを、次のフックで落とす（ほかのエージェントの hand-back は落とさない）。
  - `prompt.attachment`（type `queued_command`）：`{ text: null }` で、そのリクエストから外す。メインでも、probe を呼んだサブエージェントのループでも効く。行は先に保存され（`session.append`）、リクエストは保存された形を運ぶので、ここに届くのは下のスタブに切られたあとの形になる（2026-11-05 の記録で、外したはずの hand-back がスタブの形でリクエストに入っていた）。そこで、スタブだけの添付も外す。このとき、system-reminder の塊と、使ったツールの注記（`<tools-used-before-summary>`）は除いて判定する。この注記は、親にまだ知らせていないツールを送り主が使ったときに、エンジンが配送に添えるもので、probe の子については親に要らない（答えはツールの結果にある）。保存された行では注記は system-reminder に包まれているが、`prompt.attachment` に届く文面では包みが外れている（エンジンが全体の外側に付け直すため）。2026-11-05 の記録で、包みのない注記が残ったせいでスタブが外れず、親に届いていた。ユーザーが作業中に送るメッセージは「The user sent a new message while you were working:」の行のあとに置かれるので（保存される行は `prompt` に本文だけを持ち、この行は描画のときに付く）、スタブを引用していても外れない。
  - `prompt.submit`（origin が peer など）：`{ drop }`。
  - `session.append`（上の origin と task-notification、または door が attachment/delivery）：行は拒否できないので、本文を1行のスタブに置き換え、そのスタブを `prompt.attachment` が外す。走っているターンに届く完了の task-notification も `queued_command` の添付になるので、同じようにスタブにする。ただし、エンジンが origin を task-notification とした行だけにする。ユーザーのメッセージも system-reminder に包まれていて、本文では通知と見分けられないため。
  - 送り主は agentId、またはエンジンが付けた名前で判定する（起動時に覚える）。完了の task-notification も、task-id がすべて probe のときだけ落とす。答えの受け取り（`turn.complete`）は影響を受けない。
- デバッグ用のトレース：環境変数 `PROBE_TRACE` にファイルの絶対パスを入れると、配送らしいもの（`<agent-message`、`<cross-session-message`、`[Subagent hand-back]`、`<task-notification>`、スタブ、`<tools-used-before-summary>` のどれかを含むもの）を、各フックが見たとおりに1行の JSON でそのファイルに追記する（hook、判定、type、door、origin、agentId、turnId、本文の先頭2000文字）。`prompt.attachment` は、種類を絞らないフック（hook は `prompt.attachment (any)`）でも、判定の前の文面を書き出す。環境変数がなければ、プラグインの保存領域（`~/.claude/plugins/store/probe_*.json`）の `trace` を読む。起動中のセッションには環境変数を渡せないので、こちらを使う（ファイルを書き換えたあと `/reload-plugins` をしたら効いた。しない場合は確かめていない）。どちらも未設定か空なら何もしない。
  - 同じファイルに、差し戻しの送信結果（`hook: rewrite`、`delivered`、失敗なら `reason`）も1行ずつ書く。

## 手元のディレクトリから読み込む

`~/.claude/settings.json` の `env.CLAUDE_CODE_PLUGIN_DIRS` にこのディレクトリの絶対パスを足し（複数はコロン区切り）、Claude Code を再起動する。

## 環境変数 `PROBE_SANDBOX`

`PROBE_SANDBOX=off`（この値だけ。未設定・空・`on`・`OFF` など、ほかは今までどおり）のとき、probe の子の Bash をサンドボックスで包まず、読み取り専用の確認もせず、そのまま実行する。サンドボックスの有無も確かめない。環境変数は呼び出しのたびに読む。

使うのは、使い捨てのコンテナの中だけにする。ベンチマーク（SkillsBench など）の試行は、試行ごとに作り直すコンテナの中で動く。書き込みはコンテナごと捨てられ、守りたいホストの作業ツリーもないので、コンテナそのものが隔離になっている。逆に、権限のないコンテナの中では bwrap が使えないこと（ユーザー名前空間を作れない）が多く、そのままだと読み取り専用と判定できるコマンドしか動かず、テストやビルドを走らせられない。ホストで動かすときは設定しない。

変わらないもの：Edit・Write・NotebookEdit の拒否、`run_in_background` の拒否、子のモデル（haiku）、ツールの説明文と子への指示（読み取り専用と書いたまま。子はそのつもりで動く）。変わるもの：子の Bash がどこにでも書ける。コンテナの中のファイルは、判定が読むものも含めて子が書き換えうる。

## 制約

- サンドボックスがない環境では、読み取り専用と判定できるコマンドしか動かない（上を見る）。Bash の呼び出しごとに独立で、`cd` などは次の呼び出しに残らない。
- 権限確認：サブエージェントは親の権限モードを引き継ぐ。manual モードでは、probe の子の Bash は断られる（`claude -p` で確かめた）。
- 結果は1問い `max_chars`（既定 2000）字に収める。超えたら書き直させ、それでも超えたら切り詰める（全文を保存するファイルは作らない）。差し戻しで同じエージェントの hand-back と task-notification がもう一度出るが、エージェントの id は覚えているので、上の仕組みでそのまま落ちる。
- 時間切れの途中報告：問いが15分たっても答えを返していないときは、すぐには止めず、子に「時間切れ。ここまでで分かったことを、ふつうの答えと同じ決まりで書く」と送る（書き直しと同じ `$.session.send`。動いている子は次のモデルの呼び出しで読む）。それから2分の間、子のツールの呼び出しは、答えを返す SubagentHandback を除いてすべて断る（一番内側の `tool.call` のフックと、context ツールのフックで）。返ってきた答えはふつうの答えと同じに扱うが、差し戻しはしない。字数の上限を超えていれば切り詰める。2分で返らなければ止めて「ERROR: タイムアウト（15 分）。途中までの答えも 2 分で返らなかった。…」を返す。送れなかったときは、今までどおりすぐに止める。
- 〔〕：probe が付ける印（切り詰め、問いの見出し）は 〔〕 で書き、子の答えの中の 〔〕 は （） に変える（字数は変わらない）。子が印を書いても、親には偽物と分かる。過去の答え 226 件で 〔〕 は 0 件なので、変えて困ることはほぼない。説明文には「〔〕 は probe が付ける印」とだけ書く。
- 節約の見積もり：メインの会話から呼んだ probe の呼び出しごとに、親が自分で同じことを調べた場合との API 料金の差を、その呼び出しの行（ツール呼び出しの欄）の下に1行出す（「推定節約0.83$(API相当)　Probe未使用と比較し87%削減」）。割合は、推定節約を「probe 未使用時の費用」（減る側の合計 1a + 1b + 2 + 4。probe を使わなければ親が払っていた分）で割ったもの。どちらでも同じだけかかる部分（probe を呼んだリクエストが文脈を1回読む分など）は、分子にも分母にも入れない。減る側が 0 のとき（子がツールを使わなかった）は割合を出さない。行は `ui.render`（component `ToolUse`）で probe の行の描画に足す。見積もりは次のリクエストが記録に書かれてから出せるので、そのときに `$.state`（呼び出しの tool_use_id ごと）に書き、行を描き直させる。同じリクエストでまとめて呼んだ probe は1つの見積もりにまとめ、最後の呼び出しの行に「（probe n 件分）」を添えて出す。モデルには送られず、会話の記録（jsonl）にも残らない。サブエージェントから呼んだ probe には出さない。
  - 計算は、2026-11-05 に試したスクリプト（Python）と同じ。JavaScript に移し、そのスクリプトとこのセッションの記録（呼び出し 23 回）で、呼び出しごとの値が小数第3位まですべて一致することを確かめた。
  - 材料：親の会話の記録（`<設定のディレクトリ>/projects/<プロジェクト>/<セッション ID>.jsonl`）と、子の記録（`<セッション ID>/subagents/agent-<子の ID>.jsonl`）。設定のディレクトリは `CLAUDE_CONFIG_DIR`、なければ `~/.claude`。プロジェクトのディレクトリは、セッション ID の記録を持つものを探す。`$.fs.read` は 4 MiB を超えるファイルを読めないので、親の記録が大きいときは末尾の 4 MiB を `tail -c` で読む（呼び出しは直近なので末尾に入っている。このセッションの末尾 4 MiB で、入っていた 9 回の値が全体を読んだときと同じだった）。`tail` のない環境（Windows）で大きい記録になると、出さない。実行中に届く値（`turn.step` の `usage`）は使わない。キャッシュの書き込みの 5 分と 1 時間の内訳がなく、同じ計算にならないため。
  - 子の対応：probe を起動したときに、呼び出しの `tool_use_id` と子の ID を結び付けておく（スクリプトは問いの文と時刻で推し量っていた）。
  - 出す時：答えの書き込み（増える 3）は、結果を受け取った次の親のリクエストの書き込みから数えるので、それが記録に入ってから出す。親のリクエストが終わるたび（`turn.step` の後）と、ターンが終わったとき（`turn.complete`）に試し、8 回試しても次のリクエストが見つからなければあきらめる。
  - 減る側（親が自分で調べた場合にかかり、probe で要らなくなった分）：1a 親の文脈 C を読み直す回数 K−1 回分、1b 調べている最中に増えた分の読み直し、2 ツールの出力などのキャッシュへの書き込み、4 親の出力。増える側：1 probe を呼んだリクエストの出力、2 子の費用（Haiku）、3 答えのキャッシュへの書き込み（その後の読み直しは数えない）。probe の後の文脈の大きさによる変化（以降の読み出し、compaction）は扱わない。
  - なぞり方：子の段階 i（1回のリクエスト）を、親の文脈 C の上でそのまま行ったとみなす。段階 i の親の文脈は C + (c_i − c_1)（c_i は子の段階 i の文脈の合計）、書き込みは子の段階 i の新しいトークン（入力 + 書き込み）、読み出しは文脈 − 書き込み。
  - 仮定（記録だけでは決まらないところ）：
    - 親も子と同じ段階を踏む（子の1段階 = 親の1リクエスト）。親が呼び出しを並列にまとめたり、探す手順が少なかったりして回数が減る効果は入れていない（減る 1a・1b・4 は多めに出うる）。
    - 問いが複数あるとき、親は問いを1つずつ順に調べる（K は、全員のツールを呼んだ段階の数の和）。ただし 1b は問いごとに C から数える（順に調べるなら前の問いの分も読み直すので、1b は少なめ）。
    - 呼び出し1回（親のリクエスト）につき、子の段階 1 のうち1回は実際に probe を呼んだリクエストに当たり、差し引きで消える。残りの K−1 回が C を読み直す。子の段階 1 の書き込み（子のシステムプロンプトと問い）は親には起きない。
    - なぞるのは子の最初の答え（ツールを呼ばずに終わった段階か、SubagentHandback だけの段階）まで。差し戻しと途中報告の後の段階は親には起きないので、なぞらない（子の費用には入れる）。答えの記録がない子は、記録のある段階をすべてツール呼び出しとして扱う。応答の記録が1つもない子は、なぞらない。
    - 答えの段階は、親が調べ終えて続きを書くリクエストに当たる。両方にあるので、読み出しの増分と書き込みだけ数え、出力は数えない。
    - 親の出力は、子（Haiku）の出力（思考を含む）で代用する。
    - 増える 1 は、probe を呼んだリクエストの出力を、思考も含めて数える。増える 3 は、結果を受け取った次のリクエストの新しいトークン（入力 + 書き込み）で、答えのほかに probe を呼んだ出力の再送や注記も含む。
    - ほかのツールと同時に呼んだときは、増える 1 を tool_use の入力の文字数（Python の `json.dumps` の書き方で数える）の比で、増える 3 を tool_result の文字数の比で、probe の分だけ数える。同じリクエストの中の probe の呼び出しはまとめて1つとして数え、1行出す。
    - 親の書き込みの単価は、読んだ記録の中の親の書き込みのうち 1 時間の期限の割合で、5 分と 1 時間の単価を按分する。子の書き込みは記録の内訳どおり。
    - Haiku と Opus で、同じ文字列は同じトークン数になる。
    - 単価は claude-api スキルの料金表（2026-10-06 時点）：Opus 5.5 は入力 4、出力 20、読み出し 0.20、書き込み 5（5 分）・8（1 時間）。Haiku 5.5 は入力 0.10、出力 0.50、読み出し 0.01、書き込み 0.125・0.20（プロンプトが 10 万トークンを超えるリクエストは入力 0.50、出力 2.50 とし、倍率も同じにする）。記録の cost-state の行（Claude Code 自身の見積もり）と、Opus の 1 時間の書き込みと Haiku の読み出し・5 分の書き込みの単価で合うことを確かめた。
    - 結果が「[Tool call interrupted」で始まる呼び出し（結果が届く前にセッションが終わった）は、親が答えを受け取っていないので出さない。子がいない呼び出しも出さない。
    - 範囲外：probe の後の文脈の大きさによる変化、親に常に載る probe の説明文と usage.md、答えが足りずにやり直す分、Web の検索料金と WebFetch の中のモデル呼び出し（両方で同じ）。
  - まだ直していない点（2026-11-05 のレビュー）：子がツールを使わなかったとき（K = 0）、親は probe を呼ぶはずのリクエストでそのまま答えられるので、probe の側が1回多く C を読むが、`max(K − 1, 0)` でその分を数えていない。問いが複数あるときの 1b の不足（そのセッションで約 0.39 ドル）。ユーザーが中断した結果（`[Request interrupted by user for tool use]`）や許可を断られた結果も、ふつうの答えとして数える。Haiku の高い単価が、リクエスト全体にかかるのか超えた分だけかは分からない（全体にかけている）。
- 1回の Bash の打ち切り（bwrap のとき）：Bash は、自分の上限（`timeout` の指定、なければ `BASH_DEFAULT_TIMEOUT_MS`、なければ2分）を過ぎたコマンドを止めずに裏に回す。裏に回ったコマンドは probe の呼び出しが終わっても動き続け、終わると完了の通知が probe を呼んだ会話に届く（2.1.318 で確かめた）。そこでサンドボックスの中で `timeout -k 2 N` をかぶせ、上限の5秒前に止める。止めたときは、そこまでの出力に「（probe が N 秒で打ち切った。…）」を足して返す。sandbox-exec と srt には標準の `timeout` がないので、かぶせない。
- サブエージェントの終了待ちは `sleep 0.5` を繰り返す（フックの10秒の持ち時間を使わないため。公式の docs も「待ちは mods API の呼び出しの中に置く。自分の Promise を待つ時間は数える」と書いている）。`sleep` がない環境（Windows）では `ping -n 2 127.0.0.1`（約1秒）で待つ。どの待ち方が使えるかは probe の呼び出しごとに最初から試し、前の呼び出しで失敗した待ち方を持ち越さない。呼び出しが中断されて待ちが終わったときは、その待ち方を使えないとみなさない（以前はこれを持ち越したため、probe の実行中に中断したあと、そのセッションの probe がすべて10秒で打ち切られていた）。結果が返るまでの遅れは最大0.5〜1秒ほど。`$.tool.call` で Agent を呼んで終わりまで待つ形は、本体が「that is $.agent.spawn」と断るので使えない（型定義の説明は古い）。
- 子のモデルは haiku だけ。入力に `model` を渡すと deny する。

## auto mode での起動の許可

auto mode のサーバー側の分類器は、モデルの応答が求めていない操作には判定を返さない。そのため、`$.agent.spawn` が probe の子を起動するときの Agent の呼び出しが、新しいセッションでは拒否されていた。そこで `tool.check` のフックで、その呼び出しだけを許す。許すのは、種類が `probe:probe` で、このプラグインが起こしたもの、またはこのプラグインの probe の呼び出しの最中に起きたものだけである（この種類はモデルには見せない）。時間切れの probe の子を止める TaskStop も同じように許す。子自身のツール呼び出しはほかのサブエージェントと同じように判定される。

子の Bash だけは例外がある。auto mode の分類器は、モデルが書いたままのコマンドを判定するので、`tool.call` で包んだあとのコマンドには判定がつかず、確認に回る（理由は「a hook changed this call's input after auto mode reviewed it」）。読み取り専用と判定されるコマンドは分類器を通らないので起きないが、`cd … && …` のような複合コマンドでは起きる。そこで `tool.check` のフックで、サンドボックスの中の子の Bash に限り、確認に回ったものを許す。設定の拒否のルールなど、拒否はそのまま通す。判定なしで動くので、サンドボックスは書き込みだけでなくネットワークも止める（読んだファイルの指示で、中身を外に送らせないため）。`PROBE_SANDBOX=off` のときは許さない。
